引言

　　在接触Scala之前，我没有接触过结构化类型系统，直到接触Scala之后，才知道Scala中的结构化类型是个什么意思，以免以后自己会忘记，所以记录下来，下面是wiki里对结构化类型系统的一个定义。

A structural type system (or property-based type system) is a major class of type system, in which type compatibility and equivalence are determined by the type’s actual structure or definition, and not by other characteristics such as its name or place of declaration. Structural systems are used to determine if types are equivalent and whether a type is a subtype of another. It contrasts with nominative systems, where comparisons are based on the names of the types or explicit declarations, and duck typing, in which only the part of the structure accessed at runtime is checked for compatibility

　　本文代码测试运行于JDK1.8和Scala2.12。

结构化类型

　　在Scala里，构建结构化类型(structural type)是通过使用type关键字，并同时定义期望的类型里所具有的方法签名和变量签名，这使开发者可能够定义一种抽象的接口，而无需定义扩展指定的特质和类来匹配类型。结构化类型常见的使用场景是用于资源管理的代码，例如结构化类型可以帮助我们确保在一段代码执行过后把资源关闭，避免我们写那些样板代码。

scala> object Resources {
     |  type Resource = {
     |   def close(): Unit
     |  }
     |  def closerResource(r: Resource) = r.close()
     | }
<console>:15: warning: reflective access of structural type member method close should be enabled
by making the implicit value scala.language.reflectiveCalls visible.
This can be achieved by adding the import clause 'import scala.language.reflectiveCalls'
or by setting the compiler option -language:reflectiveCalls.
See the Scaladoc for value scala.language.reflectiveCalls for a discussion
why the feature should be explicitly enabled.
        def closerResource(r: Resource) = r.close()
                                            ^
defined object Resources

　　我们定义一个名叫Resource的类型，赋给它一个匿名的，或者说结构化的资源定义，资源定义包含了一个抽象方法成员，然后在closeResource方法里，关闭这个对象。我们看到我们虽然可以成功定义，但是有一个warning需要我们import一个scala.language.reflectiveCalls，这个东西是什么呢，我们看看Scala Api里是怎么写的：

implicit lazy val reflectiveCalls: reflectiveCalls
Only where enabled, accesses to members of structural types that need reflection are supported. Reminder: A structural type is a type of the form Parents { Decls } where Decls contains declarations of new members that do not override any member in Parents. To access one of these members, a reflective call is needed.
Why keep the feature? Structural types provide great flexibility because they avoid the need to define inheritance hierarchies a priori. Besides, their definition falls out quite naturally from Scala’s concept of type refinement.
Why control it? Reflection is not available on all platforms. Popular tools such as ProGuard have problems dealing with it. Even where reflection is available, reflective dispatch can lead to surprising performance degradations.

　　通过阅读这个val值主要是支持当结构化类型里的一个成员存在继承关系时支持反射的操作，我们不必太关心，可以把它import进来。
　　调用closeResource来关闭System.in：

scala> Resources.closerResource(System.in)
scala> Exception in thread "main" java.io.IOException: Stream Closed

　　我们看到可以成功关闭，结构化类型还是很便利的。

嵌套结构化类型

　　结构化类型也适用于嵌套和被嵌套的类型，你可以把类型嵌套在匿名的结构化块里，我们举一个变态一点的例子，实现一个简单的嵌套抽象类型。

scala> type T = {
     |  type X = Int
     |  def x: X
     |  type Y 
     |  def y: Y
     | }                                                                                                                                         
defined type alias T                                                                  

scala> object Foo {
     |  type X = Int
     |  def x: X = 1
     |  type Y = String
     |  def y: Y = "Hello, World!"
     | }
defined object Foo

　　我们声明了一个结构化类型T，这个类型里包含两个嵌套类型：X和Y，其中X定义等同于Int，而Y保持为抽象类型，然后我们又实现一个实际对象Foo，符合结构化类型的定义。
　　我们来创建一个test方法，该方法返回对T的实例调用x方法的结果。

scala> def test(t: T) = t.x
test: (t: T)t.X

　　我们看到方法返回的类型结果是t.X，而且是编译器自动推断完成的，我们再把它的返回类型改为注入会怎么样。

scala> def test(t: T): T#X = t.x
test: (t: T)Int

　　我们看到把返回类型改为T#X后，编译器就明确知道它是个Int类型了。
　　如果我们让代码使用抽象类型Y又会怎么样呢？

scala> def test(t: T): T#Y = t.y
test: (t: T)AnyRef{
type X = Int; 
def x: this.X; 
type Y; 
def y: this.Y}#Y

　　显而易见，编译器无法识别Y到底是什么类型，所以只能允许你把它当作绝对最小的类型来使用，也就是Any，在Java中也就是Object类的意思，因为T#Y不能简单地等同于另一个类型，编译器不得不把T类型和有关T#Y的全部信息都提取出来，因为类型注入不绑定到特定实例，所以编译器可以确定类型注入是否兼容。
　　我们还发现在编译器提取到的信息里，x和y方法都是的返回类型都依赖于this，但是我们定义x和y方法的时候，我们并没有指定this，但是编译器还是把它们变成了this.X和this.Y，使返回路径依赖于this，因为X和Y类型定义于结构化类型T里，你可以用标识符X引用它，但实际上指向路径依赖类型this.X。

路径依赖和结构化类类型

　　我们上面所讲的问题，实际上也带来了一个问题，当你引用定义在另个类型里的某类型时，你就用到了路径依赖类型。当我们想把路径依赖类型带出初始作用域，编译器就需要某种方法来确保路径指向完全相同的实例。有时候最终必须使用object和val，而不是class和def。
　　我们看个例子，我们建立嵌套类型T和U，它们嵌套在单例Foo里面。

scala> object Foo {
     |  type T = {
     |   type U
     |   def bar: U
     |  }
     |  val baz: T = new {
     |   type U = String
     |   def bar: U = "Hello World!"
     |  }
     | }
defined object Foo

scala> def test(f: Foo.baz.U) = f
test: (f: Foo.baz.U)Foo.baz.U

scala> test(Foo.baz.bar)
res2: Foo.baz.U = Hello World!

　　我们看到，我们创建了一个方法，其接受Foo.bar.U作为参数，因为路径依赖类型U定义在已知是稳定的路径上Foo.baz上了，当遇到路径依赖故障时，我们可以想办法让编译器知道依赖的类型是稳定的，这样我们的类型也是良好定义的，我们通常可以用上例的做法来设定一个稳定引用路径的做法。
　　我们来看一个关于路径依赖的较为深入的例子，比较难理解，需要仔细揣摩，我们设计一个Observale特质，用作一个观察变化和通知他人的通用机制，它有两个方法，一个让观察者可以订阅，另一个可以让观察者取消订阅。观察者可以通过提供个简单的回调函数的方式来订阅Observable。订阅方法应该返回个引用，以便观察者将来能够自行取消对变化事件的订阅。通过路径依赖，我们能够强制这个引用只对原Observable实例有效。

trait Observable {
  type Handle
  val callbacks = mutable.Map.empty[Handle, this.type => Unit]

  def observe(callback: this.type  => Unit): Handle = {
    val handle = createHandle(callback)
    callbacks += (handle -> callback)
    handle
  }

  def unobserve(handle: Handle): Unit = {
    callbacks -= handle
  }

  def createHandle(callback: this.type => Unit): Handle

  def notifyListeners(): Unit = {
    for (callback <- callbacks.values) callback(this)
  }
}

　　大家看到，代码中出现了很多次this.type，this.type是Scala提供的一种机制，其指向当前对象的类型，但是与直接引用当前类型不同，this.type会随着继承而变化。unobserve方法接受在之前的observe方法赋了值的handle作为参数，并且会移除该handle，这个handle类型是路径依赖的，必须是来自当前对象，这意味着即使在不同的Observable实例上注册了相同的callback，其handle是不可互换的。
　　我们来子类化Observable：

trait DefaultHandles extends Observable {
  override type Handle = (this.type => Unit)

  override protected def createHandle(callback: this.type => Unit): Handle = callback
}

　　我们继续来定义个IntHolder类，用来持有一个整数。每次其内部值变化时，IntHolder会通知观察者，IntHolder类也提供了机制来获取和设置当前持有的整数：

class IntHolder(private var value: Int) extends Observable with DefaultHandles {
  def get: Int = value
  def set(newValue: Int): Unit = {
    value = newValue
    notifyListeners()
  }
  
  override def toString: String = "IntStore(" + value +")"
}

　　我们同时也重写了toString，方便我们打印结果，我们在REPL里测试一下：

scala> import com.hazza.observable.IntHolder
import com.hazza.observable.IntHolder

scala> val x = new IntHolder(8)
x: com.hazza.observable.IntHolder = IntStore(8)

scala> def printTwice(x: IntHolder): Unit = println(x + " " + x)
printTwice: (x: com.hazza.observable.IntHolder)Unit

scala> val handle1 = x.observe(println)
handle1: x.Handle = $$Lambda$2058/712874817@25be445f

scala> val handle2 = x.observe(printTwice)
handle2: x.Handle = $$Lambda$2059/1190857779@3b009e7b

scala> x.set(10)
IntStore(10)
IntStore(10) IntStore(10)

scala> x.unobserve(handle2)

scala> x.set(9)
IntStore(9)

　　我们在构造了IntHolder实例x后，给它注册了两个handle，set方法执行时，也确实触发了这两个观察者，然后我们用handle2移除了一个观察者，再次执行set也确实没有处罚printTwice方法。
　　我们再构造一个IntHolder对象y，然后调用y.observe(handle1)会怎么样呢？

scala> val y = new IntHolder(2)
y: com.hazza.observable.IntHolder = IntStore(2)

scala> y.unobserve(handle1)
<console>:15: error: type mismatch;
 found   : x.Handle
    (which expands to)  x.type => Unit
 required: y.Handle
    (which expands to)  y.type => Unit
       y.unobserve(handle1)
                   ^

　　我们看到，正如我们所料想的那样，会报错，很明显是类型不符合，x.type和y.type是两个不同的类型，由此可以看出，我们的observe方法生成的Handle和unobserve方法所需要删除的Handle确实是路径依赖的。
　　我们再来看一个很有趣的地方，我们依然创建两个IntStore实例，并创建一个两个观察者都能使用的callback，我们还是跟前面一样用println方法来做callback

scala> val x = new IntHolder(8)
x: com.hazza.observable.IntHolder = IntStore(8)

scala> val y = new IntHolder(8)
y: com.hazza.observable.IntHolder = IntStore(8)

scala> val callbcak = println(_: Any)
callbcak: Any => Unit = $$Lambda$2091/1532711878@2ec0ca83

scala> val handle1 = x.observe(callbcak)
handle1: x.Handle = $$Lambda$2091/1532711878@2ec0ca83

scala> val handle2 = y.observe(callbcak)
handle2: y.Handle = $$Lambda$2091/1532711878@2ec0ca83

scala> handle1 == handle2
res4: Boolean = true

　　当我们把callback同时注册到x和y实例上后，再给它们比较相等性，结果这两个handle对象居然完全相同！注意==方法对两个对象是进行运行时判等检查，适用于任意两个类型。这意味着，理论上来说，y得到的handle应该可以移除x里的观察者，但是显然这是肯定不行的。　　　　

scala> x.unobserve(handle2)
<console>:15: error: type mismatch;
 found   : y.Handle
    (which expands to)  y.type => Unit
 required: x.Handle
    (which expands to)  x.type => Unit
       x.unobserve(handle2)
                   ^

　　编译器不允许这种方法，路径依赖类型限制我们的handle必须是从同个实例的方法里生成的。尽管这两个handle在运行时是相等的，类型系统依然阻止我们用错误的handle来取消观察者，这一点很重要，因为handle的类型将来可能变化。

总结

　　Scala里的结构化类型很强大，但是涉及到路径依赖类型，就会有点复杂，而且有点难懂，我这里记录下来，也是怕以后忘记，毕竟这应该是Scala里的一个很强大的语法糖，正如上面举到的那个例子一样，如果能应用到其他场景，真的可以起到事半功倍的效果。
