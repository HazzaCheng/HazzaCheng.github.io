引言

　　在Java中，对于类而言，为了让客户获取类的一个实例，最常用的方法就是提供一个公有的构造器，然而有的时候你却希望构造器不能轻易被访问，也许也会需要许多构造器，在添加一个类成员后，需要修改很多的构造器，很麻烦，甚至只想生成一个对象，也就是单例对象，接下来，我们就讨论实现这些需求的方法。

静态工厂方法

　　我们不仅可以通过公有的构造器让客户获取类的实例，还可以通过提供一个公有的静态工厂方法，它只是一个返回类的实例的静态方法，因此可以将构造器声明成私有的，通过静态工厂方法来获得类实例，下面是一个例子。

public class Examples {
    private Examples() {}

    public static Examples newInstances() {
        return new Examples();
    }
}

优势

　　类可以通过静态工厂方法来提供它的客户端，而不是通过构造器。提供静态工厂方法而不是公有的构造器，这样做具有几大优势：

它们有名称

　　如果构造器的参数本身没有确切的描述正确被返回的对象，那么具有适当名称的静态工厂方法就会更容易使用，一个类只能有一个带有指定签名的构造器，我们可以通过提供两个构造器，它们的参数列表往往知只是参数类型的顺序上不同，这样可以避开这个限制，然而这样做却不好，用户永远也记不住改用哪个构造器，结果往往会调用错误的构造器，由于静态工厂方法有名称，所以它们不受这样的限制，当一个类需要多个带有相同签名的构造器时，就用静态工厂方法代替构造器，并且慎重的选择名称以便突出它们之间的区别。

不必在每次调用的时候创建一个新的对象

　　这使得不可变类可以使用预先构建好的实例，或者将构建好的实例缓存起来，进行重复利用，从而避免创建不必要的重复对象，如下面这个Boolean.valueOf(boolean)方法就从来不创建对象,静态工厂方法可以重复的调用返回相同的对象。

public static Boolean valueOf(boolean b) {
	return b ? Boolean.TRUE : Boolean.FALSE;
}

可以返回原返回类型的任何子类型的对象

　　这样我们在选择返回对象的类时就有了更大的灵活性，这种灵活性的一种应用是，API可以返回对象，同时又不会使对象的类变成公有的。
　　这项技术适用于基于接口的框架，因为在这种框架中，接口为静态工厂方法提供了自然返回类型。接口不能有静态方法，因此按照惯例，接口Type的静态工厂方法被放在一个名为Types的不可实例化的类中。例如我们可以阅读Java Collections Framework的集合接口源码来了解这一实现，也可以了解了解服务提供者框架，来了解这一灵活性的应用，这里就不细说了。

在创建参数化类型实例的时候，它们使代码变得更加简洁

　　在调用参数化类的构造器时，即使类型参数很明显，也必须指明，这通常需要你连接两次提供类型参数：

Map<String, List<String>> m = new HashMap<String, List<String>>();

　　随着类型参数变得越来越长，越来越复杂，这一冗长的说明也很快变得痛苦起来。但是有了静态工厂方法，编译器就可以替你找到类型参数。这被称作为类型推导，例如，假设HashMap提供了这个静态工厂：

public static <K, V> HashMap<K, V> newInstance() {
	return new HashMap<K, V>();
}

　　你就可以下面这句简洁的代码代替上面这段繁琐的声明：

Map<String, List<String>> m = HashMap.newInstance();

缺点

　　同时，静态工厂方法也有许多缺点：

不含公有的或者受保护的构造器，就不能被子类化。

　　对于公有的静态工厂所返回的非公有类，也同样如此。例如，要想将Collections Framework中的任何方便的方法实现类子类化，这是不可能的。

它们与其他的静态方法实际上没有任何区别

　　在API文档中，它们没有像构造器那样在API文档中明确标识出来，因此对于提供了静态工厂方法而不是构造器的类而说，要想查明如何实例化一个类是非常苦难的，但是我们可以记住一些惯用名称，例如valueOf，of，getInstance，newInstance，getType，newType等。
　　简而言之，静态工厂方法和公有构造器各有用处，我们需要理解它们各自的长处。静态工厂方法通常更加适合，因此切忌第一反应就是提供公有的构造器，而不先考虑静态工厂。

局限性

　　静态工厂方法和构造器都有个共同的局限性，它们都不能扩展到大量的可选参数。

构建器

　　为了解决静态工厂方法和构造器的局限性，我们应该怎么做呢，我们先举一个这样的类的例子，这个例子来自《Effective Java》，这个类来表示食品包装外的营养成分标签。 这些标签中有几个域是必须的:每份含量,每罐含量。也有一些可选域：每份的卡路里含量,总脂肪量，饱和脂肪量，转换脂肪，胆固醇，纳等等。

重叠构造器

　　对于这样的类，我们习惯采用重叠构造器模式，在这种模式下，你提供第一个只要必要参数的构造器，第二个构造器有一个可选参数，第三个有两个可选掺时，以此类推，最后一个构造器拥有所有可选参数，下面是一个例子,只提供四个可选域。

public class NutritionsFacts {
    private final int servingSize;           //required
    private final int servings;              //required
    private final int calories;              //optional
    private final int fat;                   //optional
    private final int sodium;                //optional
    private final int carbohydrate;          //optional

    public NutritionsFacts(int servingSize, int servings) {
       this(servingSize, servings, 0);
    }
    public NutritionsFacts(int servingSize, int servings, int calories) {
        this(servingSize, servings, calories, 0);
    }
    public NutritionsFacts(int servingSize, int servings, int calories, int fat) {
        this(servingSize, servings, calories, fat, 0);
    }
    public NutritionsFacts(int servingSize, int servings, int calories, int fat, int sodium) {
        this(servingSize, servings, calories, fat, sodium, 0);
    }
    public NutritionsFacts(int servingSize, int servings, int calories, int fat, int sodium, int carbohydrate) {
        this.calories = calories;
        this.servingSize = servingSize;
        this.servings = servings;
        this.fat = fat;
        this.sodium = sodium;
        this.carbohydrate = carbohydrate;
    }
}

　　当你想要创建实例的时候，就利用参数列表里最短的构造器，但该列表里中需要包含了要设置的所有参数。

NutritionsFacts cocaCola = new NutritionsFacts(250, 8, 100, 0, 35, 27);

　　即使你不想给fat赋值，但是因为要给后面的sodium和carbohydrate赋值，你也必须给fat赋值为0，所以这个构造器调用通常需要许多你本不想设置的参数，但是不得不给它们赋值，当参数数目越来越多后，达到几十甚至上百后，它很快就会失去控制。
　　总结一下，***重叠构造器模式行，但是当有许多参数的时候，客户端代码会很难编写，并且仍然难以阅读。***例如，你一不小调换了两个参数的位置，这两个参数恰好类型又相同，编译器也不会报错，但是程序在运行时会出现错误的行为。

JavaBeans

　　遇到许多构造器参数的时候，还有第二种代替方法，即JavaBeans模式，在这种模式下，调用一个无参构造器来创建对象，然后调用setter方法来设置每个必要的参数，以及每个相关的参数。

public class NutritionsFacts {
    private int servingSize = -1;           //required,no default value
    private int servings = -1;              //required,no default value
    private int calories = 0;               //optional
    private int fat = 0;                    //optional
    private int sodium = 0;                 //optional
    private int carbohydrate = 0;           //optional

    public NutritionsFacts() {}

    public void setCalories(int calories) {
        this.calories = calories;
    }

    public void setSodium(int sodium) {
        this.sodium = sodium;
    }

    public void setServingSize(int servingSize) {
        this.servingSize = servingSize;
    }

    public void setServings(int servings) {
        this.servings = servings;
    }

    public void setFat(int fat) {
        this.fat = fat;
    }

    public void setCarbohydrate(int carbohydrate) {
        this.carbohydrate = carbohydrate;
    }
}

　　这样通过将必选参数设置为-1，将可选参数给上一个默认值0，可以弥补构造器模式的不足，创建实例很容易，产生代码阅读起来也很容易：

NutritionsFacts cocaCola = new NutritionsFacts();
cocaCola.setServingSize(250);
cocaCola.setServings(8);
cocaCola.setCalories(100);
cocaCola.setSodium(35);
cocaCola.setCarbohydrate(27);

　　这样就不需要给不需要的fat单独赋值。
　　然而JavaBeans模式自身有着几个严重的不足：

  • 因为构造过程被分到几个调用中，在构造过程中，JavaBean可能处于不一致的状态，类无法仅仅通过检验构造器参数的有效性来保持一致性，试图使用处于不一致状态的对象，将会导致失败。
  • 于此相关的另一点，JavaBeans模式阻止将类做成不可变的可能，这就需要程序员付出额外的努力来确保它的线程安全。

Builder模式（构建器）

　　还有第三种方法，既能保证像重叠构造器模式那样的安全性，也能保证像JavaBeans模式那么好的可读性，这就是Builder模式，不直接生成想要的对象，而是让客户端利用所有必要的参数调用构造器(或者静态工厂)，得到一个builder对象，然后客户端在builder对象上调用类似于setter的方法，来设置每个可选参数。最后，客户端调用无参的build方法来生成不可变对象。这个builder是它构建的类的静态成员类，下面就是它的用例：

public class NutritionsFacts {
    public static class Builder {
        //required parameters
        private final int servingSize;
        private final int servings;

        //optional parameters, initialized to default values
        private int calories = 0;
        private int fat = 0;
        private int sodium = 0;
        private int carbohydrate = 0;

        public Builder(int servingSize, int servings) {
            this.servingSize = servingSize;
            this.servings = servings;
        }

        public Builder calories(int val) {
            calories = val;
            return this;
        }
        public Builder fat(int val) {
            fat = val;
            return this;
        }
        public Builder sodium(int val) {
            sodium = val;
            return this;
        }
        public Builder carbohydrate(int val) {
            carbohydrate = val;
            return this;
        }

        public NutritionsFacts build() {
            return new NutritionsFacts(this);
        }
    }

    private NutritionsFacts(Builder builder) {
        servingSize = builder.servingSize;
        servings = builder.servings;

        calories = builder.calories;
        fat = builder.fat;
        sodium = builder.sodium;
        carbohydrate = builder.carbohydrate;
    }
}

　　注意，NutritionsFacts本身是不可变的，所有的默认参数值都单独放在一个地方。builder的setter方法返回builder本身，以便可以把调用链接起来：

NutritionsFacts cocaCola = new NutritionsFacts.Builder(250, 8).calories(100).sodium(35).carbohydrate(27).build();

　　这样客户端代码就很容易编写，更为重要的是，易于阅读。builder模式模拟了具名的可选参数。

检验约束条件

　　builder像个构造器一样，可以对其参数强加约束条件。builder方法可以检验这些约束条件，将参数从builder拷贝到对象中，并在对象域而不是builder域中对它们进行检验，如果违反任何约束条件，build方法就应该抛出IllegalArgumentException。
　　对多个参数强加约束条件的另一种方法是，用多个setter方法对某个约束条件必须持有的所有参数进行检查。如果该约束条件没有得到满足，setter方法就会抛出IllegalArgumentException。这个好处就是一旦传递了无效参数，立即就发现约束条件失败，而不是等着调用build方法。

优势

  • 与构造器相比，builder可以有多个可变参数。构造器就像方法一样，只能有一个可变参数。因为builder利用单独的方法来设置每个参数，你想要多少个可变参数，它们就可以有多少个，直到每个setter方法都有一个可变参数。
  • 十分灵活，可以利用单个builder构建多个对象，builder的参数可以在创建对象期间进行调整，也可以随着不同的对象而改变，builder可以自动填充某些域。
  • 当需要添加参数时，很方便，如果一开始使用构造器或者静态工厂，等到类需要多个参数时才添加构建器，就会无法控制，那些过时的构造器或者静态工厂方法显得特备不协调。
  • 设置了参数的builder生成了一个很好的抽象builder传给方法，是该方法能够为客户创建一个或者多个对象。要使用这种方法，需要有个类型来表示builder，可以使用一个泛型就能满足所有的builder，无论它们在构建哪种类型的对象。
public interface Builder<T> {
	public T build();
}

缺陷

　　Builder模式比重叠构造器模式更加冗长，因此它只在有很多参数的时候才使用，而且在某些十分注重性能的情况下，构建器的开销可能显得稍微比较大。

Singleton(单例)对象

　　实现单例对象有三种方法，我们依次来介绍一下。

公有静态成员是final域

public class Example {
	pubils static final Example INSTANCE = new Example();	
	private Example() {}
}

　　如上面的例子所示私有构造器仅被调用一次，用来实例化共有的静态域Example.INSTANCE。由于缺少公有的或者受保护的构造器，所以保证了Example全局的唯一性，一旦Example被实例化，只会存在一个Example实例。
　　但要提醒一点，享有特权的客户端用户可以借助AccessibleObject.setAccessible方法，通过反射机制调用私有构造器。如果需要抵御这种攻击，可以修改构造器，让它在被要求创造第二个实例的时候抛出异常。

公有的成员是个静态工厂方法

public class Example {
	private static final Example INSTANCE = new Example();
	private Example() {}
	public static Example getInstance() { return INSTANCE; }
}

　　对于Example.getInstance的所有调用都会返回同一个对象引用，所以永远都不会有其他的Example的实例。

优势

  • 提供了灵活性，在不改变其API的前提下，我们可以改变该类是否应该为Singleton的想法。工厂方法返回该类的唯一实例，但是它很容易被修改，比如改成每个调用该方法的线程返回惟一的实例。
  • 与泛型有关，这里不细说了。

缺陷

　　包括第一种方法，在实现其中一种方法的Singleton类变成可序列号化，仅仅在声明上加上"implements Serializable"是不够的，为了维护并保证Singleton,必须声明所有实例都是瞬时的，并提供一个readResolve方法。否则，每次反序列化一个序列化的实例时，都会创建一个新的实例。比如说在我们的Example类中加入这个readResolve方法：

private Object readResolve() {
	return INSTANCE;
}

枚举类型

　　最后一种方法，只需编写一个包含单个元素的枚举类型：

public enum Example {
	INSTANCE;
}

　　这种方法在功能上与公有域方法想近，但是它更加简洁，无偿的提供了序列化机制，即使在面对复杂的序列化或者反射攻击时，绝对防止多次实例化。单元素的枚举类型已经成为实现Singleton的最佳方法。

不可实例化

　　在实际编程过程中，有些工具类是不希望被实例化的，实例对它毫无意义。然而在缺少显示构造器的情况下，编译器会提供一个公有的、无参的缺省构造函数。企图通过将类做成抽象类来强制该类不可被实例化，这是行不通的。该类可以被子类化，并且该子类也可以被实例化。
　　我们可以通过让这个类只包含私有构造器，它就不能被实例化了，这种习惯也有副作用，它使得一个类不能被子类化，因为所有的构造器都必须是显示或隐式地调用超类构造器，在这种情况下，子类就没有可访问的超类构造调用了。

总结

　　Java中对象的创建有很多学问，也有很多模式，需要不断的学习和实践，才能理解每种模式的优势与缺陷。构造器的构建方法有很多，静态工厂方法通常比较实用，也比较方便，但是当参数过多的时候，我们可以考虑用构建器的方法。在构建单例对象的时候，如果想要简化序列化和反序列化的复杂，还有抵御反射，我们可以使用枚举类型来实现Singleton。最后，我们还可以通过私有构造器来实现对象的不可实例化，这主要用在工具类的创建时。
