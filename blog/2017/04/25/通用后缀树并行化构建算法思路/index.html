引言

　　最近刚刚参加完第三届全国高校云计算应用创新大赛，我做的是技能赛第二题，前前后后做了半年，第二题是利用spark并行化构建通用后缀树的题，算法本身还是比较复杂的，所以遂把它记录下来。

问题描述

　　序列分析是数据处理过程中一种典型分析方法，实际应用中很多数据都可以用序列的方式描述，例如生物的 DNA 或者蛋白质序列、文本中的字符串序列、具有时序特征的事件序列等。随着序列规模的越来越大，传统的序列分析方法，例如序列查找、序列匹配以及最长公共子序列查找等所需要的时间开销越来越大。为了提升大规模序列分析的计算性能，不少学者采用了将序列转化为后缀树，并基于后缀树进行序列分析的方式。后缀树不仅能够快速解决字符序列查找匹配的问题，而且能够应用在 DNA 序列模式查找、数据压缩、频繁长序列挖掘、代码克隆等领域。后缀树构建是基于后缀树进行序列分析过程中计算量最大、时间开销最长的一个步骤，特别是在大规模序列分析场景下，传统的单机后缀树构建算法已不能满足实际需求。希望利用 Spark 平台实现通用后缀树的并行化构建方法和算法，使后缀树构建操作能高效地在大规模序列数据集上完成。

后缀树

定义

　　一个具有 \(m\) 个词的字符串 \(S\) 的后缀树 \(T\)，就是一个包含一个根节点的有向树，该树恰好带有 \(m\) 个叶子，这些叶子被赋予从1到\(m\)的标号。每一个内部节点，除了根节点以外，都至少有两个子节点，而且每条边都用 \(\$\) 的一个非空子串来标识。出自同一节点的任意两条边的标识不会以相同的词开始。
　　后缀树的关键特征是：对于任何叶子 \(i\)，从根节点到该叶子所经历的边的所有标识串联起来后恰好拼出 \(S\) 的从 \(i\) 位置开始的后缀，即 \(S[i,…,m]\)。树中节点的标识被定义为从根到该节点的所有边的标识的串联。后缀树提出的目的是用来支持有效的字符串匹配和查询。
　　对于一个长度为 \(n\) 的原始序列 \(S\)，其后缀树具有以下几个特点：

  1. 后缀树的叶子节点个数为 n，即 \(S\) 的每个后缀都对应于一个后缀树的叶子结点。
  2. 除了根节点之外，每个内部节点至少包含两个子节点。
  3. 后缀树中的每条边的标签为原始序列的非空子序列。
  4. 同一个节点所有出边的标签首字符一定不同。

后缀树的单机算法

　　比较经典的有两种算法，分别是 McCreight 在 1976 年提出的和 Ukkonen 在 1992 年和 1995 年加以改进完善的。

  • Ukkonen，Ukkonen 算法是一个 online 算法，它与 McCreight 算法的一个显著区别是每次只对 \(S\) 的一个前缀生成**隐式后缀树（implicit suffix tree），然后考虑 \(S\) 的下一个字符 \(S[i+1]\) 并将 \(S[0...i+1]\) 的所有后缀加入到上一个阶段中生成的隐式后缀树中，形成一个新的隐式后缀树。最后用一个特殊字符将隐式后缀树自动转换成真实的后缀树。这样 Ukkonen 的一个最大优点就是不需要事先知道输入字串的全部内容，只需使用增量方式生成后缀树。和 McCreight 算法类似 ，也是采用压缩存储 Trie，以达到节省空间的目的。通过使用 implicit extensions 和 suffix link 两大技巧，时间复杂度可以达到线性。
  • McCreight算法， McCreight 后缀树构建算法是基于蛮力法，即已知输入文本串 T 的内容，逐步短插入到树中的后缀长度，直到将最后一个后缀（等于末尾那个字符）插入到前面已经生成的树中为止。它与蛮力法的区别是，\(T\) 的最后一个字符必须与前面的 \(n-1\) 个字符中的任何一个字符不同（\(n\) 是 \(T\) 的长度），即独一无二的终结符，这样生成的 Suffix Tree 的特点是，所有的后缀都终止于叶子结点，而且每个叶子结点必定对应一个后缀。也就是说，任何内部结点都不会是后缀的终止结点。

　　因为 Ukkonen 算法在并行化构建树时比较复杂，所以我在并行化构建树时，每个结点建树方法采取的是 McCreight 算法。

通用后缀树

定义

　　通用后缀树是一个包含多个序列的后缀树，普通的后缀树只能表示单个序列的后缀信息，而通用后缀树可以表示一组序列的后缀信息。

通用后缀树构建算法

　　从后缀树过渡到通用后缀树，主要的难度是如何区分两个序列，如何区分两个相同的后缀。比较简单的方法是给每个序列加上一个独一无二的后缀，但这样在后面的并行化处理的时候会加大内存的开销，也会加大垂直切分的难读，所以这里我们不采用这种方法，而是采取另外一种方法。 　　我们自己定一个 String 类型，取名为 RangeSubString 它的基本属性如下：

  • source​: 字符内容
  • start​: 字符串开始位置
  • end: 字符串结束位置
  • label: 保存该序列的信息，例如可以是文件名
  • index: 该后缀在序列中的开始位置

　　那么我们就可以通过 label 标签区别两个序列或者以及相同的后缀，例如下图中的 \(a\$\) 结点在树中虽然只是一个结点，但它实际上是两个叶子节点，有两个对象，它们的 \(label\) 标签分别是 \(txt1\) 和 \(txt2\)，这样我们就可以只给所有序列添加一个独一无二的终结符就可以了。

并行化策略

　　这里我们主要参考了一篇 Era 的论文，并结合上了自己的一些优化。

大体思路

  1. 生成终结符
  2. 垂直切分-预处理
  3. 垂直切分
  4. 建立子树
  5. 后处理，切分公共前缀

垂直切分

原理

　　所谓垂直切分，即根据所有后缀的前缀出现的频率，确定一些前缀出来，以这些前缀在每个结点上建立每一棵子树，这样可以保证资源分配较为平均，负载较为平衡，提升算法的效率，每个前缀的频率我们可以通过一个wordcount来计算出来，具体的伪代码：

　　伪代码中的 \(F_M\) 代表切分度，也就是这个前缀出现的频率上限，在这个切分度以内，就可以人认为是该前缀完成了切分，否则的话需要进一步的迭代扩展这个前缀的长度，直至在切分度的区间之内，当然也不能意味的进行迭代，可以设置一下最高的迭代次数，以保证算法的最优性。具体切分度的计算可以用到这个公式：

\[ F_M = \frac{MTS}{2 \cdot sizeof(tree\_node)} \]

压缩后缀

复杂度

　　因为算法需要生成每一个后缀，如果将每一个后缀都生成的话，那么这样空间复杂度是 \(O(N^2)\) 的，这对于内存来说是无法接受的，我们需要将字符串进行压缩，以此来把空间和时间复杂度都降为 \(O(N)\)。

压缩和解压缩

　　下图为压缩和解压缩的示意图： 　　首先根据前面得到的前缀，根据所有前缀中的最长的长度，对所有后缀进 slide 操作，缩短后缀的长度，即完成了压缩的任务，然后进行 groupBy 操作，切分成每个任务，最后根据​ RangeSubString​ 保存的 ​label​ 和 index​ 属性，将压缩后的后缀进行解压缩，建立子树。

groupBy

暴力查找

　　为了提高建立子树的效率，避免每一次都需要遍历所有后缀进行分组，我们可以调用 Spark 的 groupBy 操作，在进行 groupBy 操作时，我们需要所有前缀以及压缩的后缀，如果每个压缩的后缀在前缀中暴力查找的话，复杂度是 \(O(M \cdot N)\)。

前缀树查找

　　为了避免查找，我们可以进行一个优化，因为所有前缀都要发到各个节点上，为减少内存和传输的开销，我们将所有前缀建立成一棵前缀树作为广播变量后发到每一个节点上，这样不仅减少了内存上的开销，而且提高了压缩后的后缀的查找效率，将复杂度降为了\(O(L*N)\)。

一些内存优化

字符串常量池

　　因为文件名和前缀会多次用于计算，出现大量重复，浪费类内存上的开销，所以我们利用 String 的 intern() 方法扩充常量池，将所有读取的文件名以及压缩后的前缀调用 intern 方法，将其加入字符串常量池。

非递归遍历

　　建立完子树，遍历整棵树，输出信息时，如果一次性遍历，需要保存所有的数据，数据占据内存较大，尤其是对于百万，千万后缀级的子树，会造成很大的开销。所以可以采用非递归的遍历方法，不需要将中间结果存放于内存中。

结果

局限性

　　ERA 这篇论文采取的存储模式是集中存储的，也就是说要将所有序列，以及生成的后缀发到每个结点上去，也就是在内存中计算，这样如果你的服务器性能较好，1G 的序列内存可能勉强可以处理，但是如果当数据量达到几十，甚至 TB 级，这样的方式肯定是不行的，内存肯定会爆掉。

思考

　　解决上述这个问题，以解决这个算法的通用性，其实可以采取共享存储的方式，也就是不要将序列以及后缀保存在内存中，二是将它们全部保存到 HDFS 这个分布式文件存储系统中，这里就会涉及到大量的 I/O 以及传输优化，可以将后缀经过排序后写入到 HDFS 里等，优化的点很多，这里就不阐述了，留给大家自己思考。
