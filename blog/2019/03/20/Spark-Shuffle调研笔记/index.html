引言

　　我们都知道shuffle是Spark的一个性能瓶颈，shuffle的性能高低直接影响了整个程序的性能和吞吐量，本文就记录下Spark Shuffle的相关实现思想，并记录下与Hadoop Shuffle的区别。

Shuffle

　　我们都知道，Shuffle阶段在MapReduce计算框架中，介于Map阶段和Reduce阶段之间，当Map的输出结果要被Reduce使用时，输出结果需要按key哈希，并且分发到每一个Reducer上去，这个过程就是shuffle。由于shuffle涉及到了磁盘IO和网络IO，因此shuffle性能的高低直接影响到了整个程序的运行效率。
　　那么何时会触发shuffle呢？对于Spark来讲，一些Transformation或Action算子会让RDD产生宽依赖，即parent RDD中的每个Partition被child RDD中的多个Partition使用，这时便需要进行Shuffle，根据Record的key对parent RDD进行重新分区。
　　如下图所示，以Shuffle为边界，Spark将一个Job划分为不同的Stage，这些Stage构成了一个大粒度的DAG。Spark的Shuffle分为Write和Read两个阶段，分属于两个不同的Stage，前者是Parent Stage的最后一步，后者是Child Stage的第一步。

　　接下来我们分Shuffle Write和Shuffle Read两个阶段来简单的介绍下Spark的Shuffle实现的思想。

Shuffle Write

　　下面是shuffle write的一个简单的流程图，这里先用Hash-Based Shuffle的流程举个例子：

　　我们可以发现，每一个Mapper会根据Reducer的数量创建出相应的bucket，bucket的数量是\(M \times R\)个，其中\(M\)是Mapper的个数，\(R\)是Reducer的个数。然后Mapper会根据设置的partition算法将产生的结果填充到每个bucket中去，这里的partition算法是可以自定义的，默认的算法是根据key哈希到不同的bucket中去。最后当Reducer启动时，它会根据自己task的id和所依赖的Mapper的id从远端或是本地的block manager中取得相应的bucket作为Reducer的输入进行处理。

这里的bucket是一个抽象概念，在实现中每个bucket可以对应一个文件，可以对应文件的一部分或是其他等。

　　我们很容易发现，这种实现的问题是产生的FileSegment过多，足足有\(M \times R\)，通常Spark Application的\(M\)和\(R\)都很大，因此磁盘上会存在大量的数据文件。因为产生的FileSegment过多，导致占用缓冲区的内存空间也过大了，对于一个有\(C\)个core的worker，总共产生的临时文件达到\(M \times R\)个，同时存在的bucket达到了\(C \times R\)个（一般一个core运行一个Task），那么消耗的内存就达到了\(C * R * 32KB\)（bucket大小由spark.shuffle.file.buffer.kb指定 ，默认是32KB），对于对于8核1000个reducer来说，占用内存就是256MB，还是非常吃内存的。
　　而且，Map的输出必须先全部存储到内存中，然后写入磁盘。这对内存是一个非常大的开销，当内存不足以存储所有的Map output时就会出现OOM。
　　为了解决shuffle文件过多的情况，Spark 0.8.1引入了新的shuffle consolidation，以期显著减少shuffle文件的数量。

　　如上图所示，改进后的shuffle，可以明显看出，在一个core上连续执行的ShuffleMapTasks可以共用一个输出文件ShuffleFile。先执行完的ShuffleMapTask形成一个ShuffleBlock，后执行的ShuffleMapTask可以将输出数据直接追加到前一个ShuffleBlock后面，再形成一个新的ShuffleBlock，每个ShuffleBlock被称为FileSegment。下一个stage的reducer只需要fetch整个ShuffleFile就行了。这样，每个worker持有的文件数降为\(C \times R\)个。并且与之前Map的输出全部存储在内存中，再flush到硬盘，现在是record-by-record写入到磁盘中的文件里。

File Consolidation 功能可以通过spark.shuffle.consolidateFiles=true来开启。

　　对于Spark Shuffle，Spark中先后实现了三个Shuffle算法，Hash-Based Shuffle，Sort-Based Shuffle和Tungsten-Sort Shuffle，我们分别简单的介绍一下。

Hash-Based Shuffle

　　Hash-Based Shuffle是Spark 1.2之前的默认Shuffle实现，并在Spark 2.0版本中被移除，我们上面叙述shuffle write的流程就是Hash-Based Shuffle，我们通过上面的分析，可以看出，就算经过consolidate机制优化后，如果Reducer端的并行数据分片过多的话则\(C \times R\)依然过大，依然很吃内存。所以如果使用Hash-Based Shuffle，Spark不能够处理大规模的数据，Spark不能够运行在大规模的分布式集群上。

Sort-Based Shuffle

　　自Spark 1.6以来，Spark默认使用Sort-Based Shuffle，他要解决的核心问题就是减少Mapper端ShuffleWriter所产生的文件数量。

　　如上面两张图所示，Sorted-Based Shuffle不会为每个Reducer中的Task生产一个单独的文件，相反Sorted-Based Shuffle会把Mapper中每个ShuffleMapTask所有的输出数据Data只写到一个文件中，因为每个ShuffleMapTask中的数据会被分类，所以Sort-based Shuffle使用了index文件存储具体ShuffleMapTask输出数据在同一个Data文件中是如何分类的信息。因此基于Sort-based Shuffle会在Mapper中的每一个ShuffleMapTask中产生两个文件，一个Data文件和一个Index文件，文件的总数量也就变成了\(2 \times M\)。
　　其中Data文件是存储当前Task的Shuffle输出的，而Index文件则存储了Data文件中的数据通过Partitioner的分类信息，此时下一个阶段的Stage中的Task就是根据这个Index文件获取自己所需要抓取的上一个Stage中ShuffleMapTask所产生的数据。
　　在图中，我们也看到有ExternalSorter，在Mapper阶段它要进行排序，类似二次排序，它根据2个Key进行排序，第一个是PartitionId进行排序，第二个是就是本身数据的Key进行排序，它不是一个全局排序，在Mapper端进行排序的过程其实是让Reducer去抓取数据的时候变得更高效，比如说第一个Reducer，它会到Mappr端的索引为特定PartitionId的数据分片中抓取数据。
　　对于Reducer而言，Reducer首先找Driver去获取父Stage中每个ShuffleMapTask输出的位置信息，跟据位置信息获取Index文件，解析Index文件，从解析的Index文件中获取Data文件中属于自己的那部份内容。
　　一个Mapper任务除了有一个数据文件以外，它也会有一个索引文件，Map Task把数据写到文件磁盘是顺序根据自身的Key写进去的，也同时按照Partition写进去的，因为它是顺序写数据，记录每个Partition的大小。
　　理解了Sort-Based Shuffle的原理，我们也可以分析出它的缺点，它强制了在Mapper端要排序，如果本身数据根本不需要排序的话，这是一个多余的开销。并且它是要基于记录本身去进行排序的，这也带来了很大的性能消耗。而且还是文件数量的问题，如果Mapper端并行的partition过多的话，也会导致大量内存消耗和GC的巨大负担。

Tungsten-Sort Shuffle

　　Tungsten Project是Databricks提出的对Spark优化内存和CPU使用的计划，该计划初期似乎对Spark SQL优化的最多。不过部分RDD API还有Shuffle也因此受益。它自Spark 1.4开始被引入，并且在Spark 1.6时Tungsten-sort并入Sort-Based Shuffle由SortShuffleManager自动判断选择最佳Shuffle方式，如果检测到满足Tungsten-sort条件会自动采用Tungsten-sort Shuffle，否则采用Sort-Based Shuffle。
　　它为了优化Sort-Based Shuffle还存在的一些问题，主要由三方面的改进：

  • 直接在serialized binary data上sort而不是java objects，减少了memory的开销和GC的overhead。
  • 提供cache-efficient sorter，使用一个8bytes的指针，把排序转化成了一个指针数组的排序。
  • spill的merge过程也无需反序列化即可完成

　　它也有一些限制条件：

  • Shuffle dependency 不能带有aggregation 或者输出需要排序。
  • Shuffle的序列化器需要是KryoSerializer或者Spark SQL自定义的一些序列化方式。
  • Shuffle文件的数量不能大于16777216，序列化时，单条记录不能大于128MB，原因也是因为它自己管理的二进制序列化后的数据以及数组指针管理范围。

　　因此，我们总结下，Tungsten-Sort Shuffle在Mapper中不会对内部元素进行排序（它只会对Partition进行排序），原因是它自己管理的二进制序列化后的数据。数据的排序是发生在Buffer要满了spill到磁盘时才进行排序的。如果不能满足上面列的那些限制条件，Tungsten-Sort Shuffle会退化成为Sorted-Based Shuffle。
　　具体实现细节这里就不探究了，有兴趣可以研究研究源码。

Shuffle Read

　　Shuffle Read的过程其实主要就是fetch和aggregate的过程。

fetch

　　在Hadoop MapReduce中，Reducer可以在Mapper执行占比到某个阀值时就可以开始拷数据了，然后真正的执行等拉取到所有依赖的map结果后开始执行。但在Spark中，因为Spark是按照Stage线性执行的，前面的Stage必须执行完毕，才能够执行后面Reducer端的shuffle过程，Spark一定是先完成Mapper端所有的task，才会进行Reducer端的shuffle过程。
　　Spark是倾向于优先使用内存的计算模型，fetch过来的数据首先会放在Reducer端的内存缓存区中，spark.shuffle.spill=false就只用内存，存储在AppendOnlyMap中。如果不是的话，会采取内存+磁盘的策略，存储在ExternalAppendOnlyMap中，如果内存空间不足时，ExternalAppendOnlyMap可以将KV records进行sort 后spill到磁盘上，等到需要它们的时候再进行归并。
　　一个ShuffleMapStage形成后，会将该stage最后一个final RDD注册到Driver上的MapOutputTrackerMaster，Mapper通过和MapOutputTrackerMaster来汇报ShuffleMapTask具体输出数据的位置 (具体的输出文件及内容是和Reducer有关的)，然后Reducer向Driver中的MapOutputTrackerMaster 请求数据的元数据信息，然后和Mapper所在的Executor进行通信，有两套不同的框架去fetch数据，NIO通过socket连接去fetch数据，OIO通过netty server去fetch数据。

aggregate

　　因为fetch来的FileSegments要先在内存做缓冲，所以一次fetch的FileSegments总大小不能太大，Spark规定这个缓冲界限不能超过spark.reducer.maxMbInFlight。Hadoop MapReduce shuffle阶段是边fetch边使用combine进行处理，只是combine处理的是部分数，为了让进入reduce的records有序，必须等到全部数据都shuffle-sort后再开始reduce。因为Spark不要求shuffle后的数据全局有序，因此没必要等到全部数据shuffle完成后再处理。 　　Spark使用了aggregate的数据结构，来实现边shuffle边处理，而且流入的records是无序的。比如用HashMap，每个shuffle得到（从缓冲的FileSegment中反序列化出来）一个KV record，直接将其放进HashMap里面。如果该HashMap已经存在相应的Key，那么直接进行aggregate也就是hashmap.update(hashMap.get(Key),hashMap.get(Key)+Value))，对应到WordCount上就是在hashmap里不断更新word的计数，等到数据aggregate好以后进行reduce。
　　因此，为了能够存放所有数据，用户必须确保每一个partition足够小到内存能够容纳，这对于内存是一个非常严峻的考验。因此Spark文档中建议用户涉及到这类操作的时候尽量增加partition，也就是增加Mapper和Reducer的数量。

与Hadoop的区别

　　Hadoop MapReduce和Spark的Shuffle过程大体上是相似的，都是将Mapper（Spark里是ShuffleMapTask）的输出进行partition，不同的partition送到不同的Reducer（Spark里Reducer 可能是下一个stage里的ShuffleMapTask，也可能是ResultTask）。Reducer以内存作缓冲区，边shuffle边aggregate数据，等到数据aggregate好以后进行reduce（Spark里可能是后续的一系列操作），但是也存在许多不一样的地方。
　　Hadoop MapReduce将处理流程划分出明显的几个阶段：read，map，collect，spill，combile，shuffle，merge，sort，reduce，write等，每个阶段各司其职，可以按照过程式的编程思想来逐一实现每个阶段的功能，而在Spark中，没有这样功能明确的阶段，只有不同的stage和一系列的transformation，所以spill，merge，aggregate等操作需要蕴含在transformation中。

存在的问题

　　如果你经常用Spark很大的Application的话，应该碰到过FetchFailedException，这主要是发生在Shuffle Read的时候，shuffle read的量很大，那么将会导致一个task需要处理的数据非常大，导致JVM crash，从而导致取shuffle数据失败，同时executor也丢失了，会导致Stage的重试，重新提交该 Stage和该Stage对应的ShuffleMapStage，造成了重复计算。
　　我们可以想办法减少shuffle数据，优化算子，避免数据倾斜来减少FetchFailed的发生，底层上我们也可以做一点优化，将Mapper存储到本地shuffle数据同时备份一份到HDFS上，当Reducer拿不到shuffle数据时，会从HDFS上获取对应数据，这样就不依赖被拉取数据的节点了，避免了FetchFailed的问题。
